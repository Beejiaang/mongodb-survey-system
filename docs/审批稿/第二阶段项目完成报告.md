## 二、系统设计

### 2.1 模块与职责

浏览器通过Flask路由提交表单，路由检查登录、CSRF和权限，业务层处理题型、版本、授权与统计，再通过PyMongo访问MongoDB。页面由Jinja生成，图表使用项目内的JavaScript，不增加外部问卷平台依赖。

| 模块 | 主要文件 | 本阶段职责 |
| --- | --- | --- |
| 题目与版本 | question_library.py、library_views.py | 创建、引用、历史、比较、恢复、分支和共享审批 |
| 数据约束 | library_schema.py、database.py | 七集合结构校验、索引和已知旧结构兼容初始化 |
| 问卷 | surveys.py、survey_views.py | 草稿调序、删除、发布锁定及题目快照 |
| 跳转与校验 | jumps.py、questions.py、numeric_input.py | 继续复用配置驱动的校验与路径计算 |
| 填写与统计 | responses.py、survey_results.py、library_results.py | 保存实际路径和答案，提供整卷、单题及跨卷统计 |

### 2.2 主要操作流程

创建者保存常用题目v1，将指定版本放入题库，再在问卷草稿中选用。修改常用题目会新增版本并更新该题目的默认版本；已有题库条目和问卷不会自动升级。草稿需要更新时，由用户明确替换；发布后题目内容锁定。

共享需求者提交指定版本的申请，出题者批准后才能使用；出题者也可主动授权。用户级授权覆盖接收者当前及未来的本人问卷，并允许建立修改分支；部分问卷授权只允许指定问卷复用原版。新版本需要新的授权，原版许可不会自动延伸。

### 2.3 权限边界

| 行为 | 权限规则 |
| --- | --- |
| 修改原题版本历史 | 仅原作者新增版本，不覆盖历史内容 |
| 修改个人分支 | 分支所有者操作，且来源用户级授权仍有效 |
| 查看问卷管理及回答 | 仅该问卷所有者；拥有题目并不获得回答权 |
| 原作者预览引用卷 | 真实引用且处于开放状态，仅只读全文；草稿、截止、关闭拒绝 |
| 撤销授权 | 阻止新的受限取用或修改，保留旧快照、历史回答及统计 |

原作者可以识别原题及其分支被哪些问卷引用，但不能据此查看接收者分支的版本历史或回答。权限判断由服务端执行，隐藏按钮不能代替接口检查。

## 三、MongoDB设计

### 3.1 集合划分

| 集合 | 主要内容 | 设计理由 |
| --- | --- | --- |
| users | _id、username、password_hash、created_at | 账号独立管理，沿用规范化用户名和密码哈希 |
| surveys | 所有者、状态、设置、嵌入题目、来源版本 | 整卷读取方便，保存实际使用的固定内容 |
| responses | 一次填写的答案、路径、状态及修订号 | 每次填写独立保存，避免多人回答覆盖同一问卷文档 |
| question_items | 题目身份、所有者、默认版、分支来源、旧卷映射 | 区分同一题目的身份与多个不可变版本 |
| question_versions | 题目内容、版本号、派生源、原默认版、恢复源 | 历史并存，可解释版本关系 |
| question_banks | 题库名称、说明及指定版本条目 | 组织常用题目；删除题库不删除题目和问卷 |
| question_shares | 版本、需求者、范围、状态及审批信息 | 使用权独立管理，保留授权与撤销历史 |

surveys.questions中的source引用题目身份及版本；responses通过survey_id及本地question_id关联问卷和题目。问卷中的本地题号与题目库版本号作用不同，替换草稿版本时保留本地题号。

### 3.2 嵌入、引用和冗余的取舍

问卷保留题目全文快照，题目版本集合保存可复用的历史内容。这部分冗余用于固定题干、选项和校验限制，保证原题升级或授权撤销后，旧回答仍能按当时的问卷解释。系统通过显式选版和发布锁定控制两处内容的关系，不追求自动同步。

题库只保存版本引用；每份回答不重复保存整套题目正文。用户、题目、授权和回答具有独立生命周期，因此分别建集合，避免把所有数据放入一份文档。字段和索引详情见[数据库设计](../数据库设计.md)。

### 3.3 为什么适合MongoDB

单选、多选、数字和文本题具有不同的嵌套字段，选项、校验条件及跳转规则可以直接保存为结构化文档。读取完整问卷、保存一次填写进度和对单文档执行条件更新，是本项目的主要访问模式，与文档模型相适应。

关系数据库同样可以实现本系统，但通常需要拆分题目、选项、规则、版本及引用关系，并在读取时组装。本项目选择MongoDB既符合课程要求，也便于保留不同题型的完整版本快照；这并不意味着MongoDB在所有场景下更快。应用仍须负责引用检查、权限和跨集合一致性，不能依赖关系型外键或默认事务来保证这些规则。

### 3.4 约束、索引和兼容性

七集合使用结构校验，应用层补充跨字段和引用合法性检查。除默认_id索引外，当前有13个业务索引，用于唯一用户名、问卷/回答查询、版本号唯一、题库归属及有效授权去重。版本号通过原子计数分配，再由唯一索引约束；默认版本指针按版本号条件更新，防止较慢请求将指针退回。

已有问卷和回答不批量改写。旧问卷保存为常用题时，通过新题目项中的original_use关联原实例，避免追加source改变旧问卷摘要。兼容初始化只接受已知结构变化，未知结构拒绝覆盖。对保留验收库的七集合进行了初始化前后数量及BSON哈希核对，见[兼容证据](../验收证据/第二阶段/范围与分支-兼容升级.json)。

## 四、跳转设计

跳转规则属于具体问卷。题目库中的版本不保存另一份问卷的本地跳转目标，导入后应在当前问卷重新配置。原有单选equals、多选contains_all/equals_set及数字eq/lt/lte/gt/gte/between继续有效，规则按顺序采用第一条命中，目标只允许指向后续题目。

草稿题目替换、调序或删除会清空全卷规则，并提示重新配置。题目内容或顺序变化后，旧表单携带的修订摘要失效，服务端拒绝过期请求。发布后的问卷仍禁止这些修改。

本轮G卷先保存“年龄等于18→第3题补充说明”，再将年龄题从原v1替换为v2。实测结果为三题题号及顺序保留、上限120变为100、跳转清空，其他问卷不变。调序、删除由P2-01～P2-05自动测试覆盖，用户决定不再继续本轮手工操作，不记为手工通过。

## 五、校验设计

创建、复制和恢复版本继续使用同一题型校验，防止新版本绕过选项数量、数字范围、整数和文本长度约束。填写时先校验答案，再计算下一题；提交时重算实际路径，只统计实际到达且正式提交的回答。

共享新增范围校验：目标问卷必须属于需求者，申请或授权所需的草稿状态正确，来源版本存在；多目标请求先检查范围，避免把其他用户问卷混入授权。派生和导入分支时再次检查来源许可，部分问卷授权不能用于建立分支。

基础数字格式、整数和上下限、文本长度、复制链接等，按用户要求沿用[第一阶段补测证据](../验收证据/手工校验补测/执行记录.json)，本阶段不重复宣称手机实测。一键添加按钮文案改为“（请使用阿拉伯数字回答）”后，39项相关检查通过，见[按钮验证](../验收证据/第二阶段/数字提示按钮-验证.json)。

### 6.2 AI帮了什么

## 八、遇到的问题

| 问题 | 对项目的影响 |
| --- | --- |
| 原来题目仅嵌入问卷 | 缺少跨卷身份，无法可靠区分同题复用及不同版本 |
| 直接覆盖原题或补写旧问卷来源 | 可能改变历史内容及修订摘要，使回答语义或填写进度失效 |
| 共享范围不断细化 | 需要同时表达用户级、指定问卷及修改分支限制 |
| 替换、调序后保留旧跳转 | 目标及条件含义可能不再成立 |
| 相同版本被多位作者引用 | 若只按version_id统计，可能混入其他所有者的数据 |
| 开发记录直接追加到报告 | 旧测试数量和“手机未执行”等过期描述与最新结果并列 |

## 九、如何解决

采用独立题目身份和不可变版本，问卷持有快照及确切来源；恢复通过新增版本实现，旧卷来源映射存放在题目项中。授权集合明确记录版本、需求者、范围和状态；读取回答时再次按问卷所有者过滤。来源许可与分支关联保存，防止通过应用中的复制、另存或转授移除限制。

草稿替换、调序和删除使用旧内容及修订摘要校验，成功操作后清空全卷跳转；已有题号尽可能保留。已发布问卷继续锁定，新的题库默认版不会自动改变其内容。测试同时检查正常路径、越权、旧表单、撤销及并发边界，并保留真实手工样本用于核对。

本次报告与测试说明按当前结论重排，历史批次通过链接追溯。原报告、用例、手工记录和第一阶段材料在审批前保留，获批后再同步正式入口，避免把审批稿当作已定稿提交材料。
